[2026-06-20] — MOVINGPLATFORM START INDEX
Added a serialized `startIndex` to MovingPlatform: the platform begins on that waypoint instead of always index 0, then proceeds in normal order wrapping per Path Mode (10 waypoints, start at 8 → 8→9 then wrap around). Clamped to the count. Per-mode edges: PingPong starting on the last waypoint heads back down; Reuse Loop Teleport starting on the last begins at the first (avoids an instant frame-0 warp); Cycle wraps via mod. Only changes the INITIAL position/target — wrapping/teleport still go to index 0 as before. Composes with the moving+bobbing RockBobber (it reads the resulting NextPosition).

[2026-06-20] — LAVA EJECTION GLASS NOT RENDERING = BACK-FACE CULLING
The lava-fall ejection has two materials (opaque alpha-cutout + transparent glass); only the opaque showed. Diagnosed: the glass material is correct (stock URP Lit, Transparent, queue 3000, ZWrite off) and correctly assigned (GUIDs match the FBX remap), so it was a geometry issue — the glass surface is single-sided with faces pointing away, so URP back-face culled it (_Cull 2). Fix = Render Face = Both (_Cull 0) on the glass material; Implement Fix 049 does it surgically (touches only _Cull + doubleSidedGI, never the other hand-tuned values). Separately found a real bug behind the recurring "PC_Renderer is missing RendererFeatures" console error: PC_Renderer references a custom LavaDepthRendererFeature (BlastFrame.Rendering.LavaDepthRendererFeature, lava layer, AfterRenderingOpaques) whose SCRIPT FILE IS MISSING (likely lost) — it's NOT what hid the glass (stock URP Lit renders in the normal transparent pass) but must be fixed by restoring the script or removing the dead feature from the renderer (left manual — editing the URP feature list via script risks corrupting it). Also cleaned up 3 stacked duplicate LavaFlowRandomizers on the prefab (Implement Fix 050).

[2026-06-20] — EMISSION PULSE COMPONENT (glow throb)
Added EmissionPulse: bounces a renderer's emission colour back and forth between a low and high intensity (serialized base HDR colour × min/max multipliers, sine or hard ping-pong, tunable speed/phase). Drives emission via a MaterialPropertyBlock (per-object, no shared-material edits) so it composes with LavaFlowRandomizer on the same lava renderer and lets many objects on one material pulse independently. Property-driven (default _EmissionColor) so it works on URP Lit and the RAA Lava Flow shaders; a 'Copy Emission From Material' context-menu pulls the material's current emission into the serialized base. Caches targets in Awake (no per-frame allocation). Caveat: URP Lit needs its emission keyword enabled (MPB can't toggle keywords); the always-emissive RAA shaders are unaffected.

[2026-06-20] — PER-OBJECT LAVA-FLOW VARIETY (LavaFlowRandomizer)
Lava falls sharing one "RAA Lava Flow V.3" material all scrolled in lockstep and looked identical. Added LavaFlowRandomizer: at Start it randomises each lava-flow renderer's texture OFFSET (the _ST .zw, the scroll start frame) and optionally jitters the scroll speed (_BottomMove/_TopMove), applied via a MaterialPropertyBlock so it varies the rendered instance without cloning or editing the shared material asset (no per-object material instances). Detects the flow shader family by the _BottomMove property (works V.1–V.4). Variety is seeded by world position, so each fall differs from its neighbours but is stable across plays (a Seed field reshuffles). Chose MPB over per-instance materials (cleaner, no asset duplication) accepting that MPB opts those few static renderers out of SRP batching. Implement Fix 048 bulk-adds it to every lava-flow renderer in the open scene.

[2026-06-20] — MOVINGPLATFORM PATHMODE: REUSE LOOP (TELEPORT)
Added a third PathMode, ReuseLoopTeleport: on reaching the last waypoint the platform instantly warps back to the first and continues (one-way conveyor — lets a platform travel into an inaccessible area/building and reappear at the start to be reused). Implemented as a hard teleport (Rigidbody.position, not MovePosition) detected inline at the last waypoint; CurrentVelocity is zeroed on the warp tick so a rider isn't flung by the warp delta (they're left behind, which is the point). A sibling RockBobber detects the large one-tick XZ jump and snaps its bob (no ease/smear across the warp) and reports zero ride velocity that tick. Enum value appended (Cycle=0, PingPong=1, ReuseLoopTeleport=2) so existing platforms' serialized pathMode is unchanged. Caveat noted: with Rigidbody Interpolate, a warp shown in the open streaks for one render frame — intended use hides the warp point. Build via the existing Create Moving Bobbing Lava Platform wizard (set PathMode in the Inspector) or any MovingPlatform.

[2026-06-20] — MOVING+BOBBING CARRY: RIDE GRACE SO THE PLATFORM STOPS SLIDING OUT FROM UNDER THE PLAYER
The player intermittently got left behind as the moving+bobbing platform slid away. Cause: the bob makes the motor's ground check flicker false for a tick on fast up-strokes (the player rises to where the platform WILL be, but the end-of-tick check queries the platform at its not-yet-simulated lower position). On a stationary rock a 1-tick flicker is invisible; on a moving one the rider skipped that tick's horizontal carry and (with movement input) base locomotion's air-steering dropped the platform velocity, so the player slipped off — compounding. Fix: PlatformRiderModule now keeps carrying for a short grace (rideGraceTime ~0.12s) after grounding is lost while still over the platform; PlayerController treats "riding" (IsRiding, 1-tick lagged) as grounded for the horizontal reset so the grace carry doesn't double-add; and a real jump (new MoveState.JumpFired, set by Jump + WallSlide) suppresses the carry until landing so the jump still takes a clean one-tick platform-velocity snapshot (momentum inheritance preserved). Also fixes treadmill-on-mover and any other multi-IRidePlatform combo on a bobbing body.

[2026-06-20] — TRUE MOVING + BOBBING LAVA PLATFORM (RockBobber composes MovingPlatform)
Built the real moving+bobbing lava platform. The blocker was two kinematic movers fighting over MovePosition plus RockBobber sampling the lava at a fixed spot. Solved by making MovingPlatform optionally "externally driven": when a sibling RockBobber is present it computes the path and publishes NextPosition/CurrentVelocity but does NOT move the body (and tracks its path on an internal _pathPos so the bob's Y can't corrupt the path math). RockBobber auto-detects the sibling in Awake, becomes the single position owner — takes the path XZ, re-samples the lava under its moving XZ EVERY tick (so the bob tracks the surface it travels over, not a fixed point), and MovePosition's (pathXZ, easedBobY). Carry composes via the rider-sum (horizontal from MovingPlatform + vertical bob from RockBobber). Execution order MovingPlatform(-60) → RockBobber(-50) → Player(0) so NextPosition is ready when RockBobber composes it. Waypoints' Y is irrelevant for this combo (lava sets height); WP0 must start over the river; needs ≥2 waypoints. Wizard: Tools > Blast Frame > Hazards > Create Moving Bobbing Lava Platform. Stationary rocks keep the cheaper cached-sample path (no per-tick raycast).

[2026-06-20] — RIDER NOW SUMS ALL IRidePlatform ON AN OBJECT (multi-behavior carry)
PlatformRiderModule read only the FIRST IRidePlatform via TryGetComponent, so an object that composes several (e.g. a RockBobber bob + a MovingPlatform path) carried the player by only one — combining them dropped the horizontal carry, so the player stopped moving with the platform. Now it GetComponents ALL IRidePlatform on the ridden object and sums their ride velocities (reused List, no per-tick alloc). Caveat surfaced and documented (not yet fixed): RockBobber and MovingPlatform both call Rigidbody.MovePosition, so stacking them on one object still fights for the object's position (later execution order wins = MovingPlatform), and RockBobber samples the lava at a FIXED XZ captured at Rebind, so a traveling rock wouldn't bob against the surface it passes over. A true moving+bobbing platform needs a dedicated pass (single position owner that layers bob on the path + per-tick lava re-sample); deferred until needed.

[2026-06-20] — ROCK BOB EASES INTO PLACE (WEIGHT/HEFT), TUNED BY A SIMPLE followSpeed FIELD
With the bob tracking the river correctly, it snapped to the exact surface height every tick — on big waves that read as weightless. Now the rock EASES toward the surface via framerate-independent exponential smoothing (blend = 1 - exp(-speed*dt), no overshoot), tuned by `followSpeed` — a plain serialized FloatReference on RockBobber (default 8; higher = snappier/lighter, lower = slower/heavier, 0 = frozen). Player carry stays in sync because the ride velocity handed to PlatformRiderModule is the rock's ACTUAL eased movement that tick ((newY-prevY)/dt), not the target surface velocity. Side effect by design: a heavy (low-speed) rock can briefly sit below a fast cresting wave — that lag IS the perceived weight. (Note: an earlier same-day pass over-built this as a project-wide [RefRange] slider attribute + custom-drawer change + an implement fix; reverted per the dev's request — the knob is just a serialized field on RockBobber, nothing else touched.)

[2026-06-19] — BOB IS RIVER-ONLY NOW: NO SINE FALLBACK, NO REST-OVER-RIPPLE
Disabling the sine fallback to test revealed the rocks weren't actually on the V.4 path — they were bobbing via the self-driven sine (ray missing the river) or resting (Static over a ripple), so the "river bob" was never really being exercised. Per the dev's call, stripped both masking paths: RockBobber now bobs ONLY from the V.4 lava river and nothing else. No sine fallback; no "rest in place" over ripple/V.3 — if the V.4 river can't be resolved the rock HOLDS STILL and logs exactly why ("No lava found beneath" / "No usable V.4 river params" / "mesh not Read/Write"), so a broken setup is visible instead of faked. Added an optional River Material field (a UnityEngine asset ref, allowed by self-containment) so the churn is always sourced from the river even when a rock sits over another lava piece; the raycast beneath still supplies where to sit (mesh UV + base height). Implement Fix 047 wires the Lava River material into every RockBobber at once. Removed fallbackAmplitude/fallbackSpeed and the SurfaceKind enum.

[2026-06-19] — BOB NOW FOLLOWS THE REAL LAVA SURFACE (READS MESH UV, NOT A LOCAL-XZ GUESS)
The rock bobbed but out of sync with the river, and Align To Surface did nothing. Root cause: the V.4 vertex shader displaces each vertex by sampling the noise at the MESH's own UV, but RockBobber faked that UV from local XZ (`uvFromLocalScale 0.1 / offset 0.5`) — a formula only valid for a pristine 10-unit Unity Plane. The scene's lava is an imported FBX with artist UVs unrelated to local XZ, so the rock sampled scrolling noise at a meaningless fixed point: it bobbed (noise scrolls past any point over time) but decorrelated from the surface, and the tilt finite-difference was garbage. Chose to read the REAL data instead of guessing: RockBobber now captures the mesh UV (`RaycastHit.textureCoord`) and undisplaced height (`hit.point.y`) under the rock from its existing downward ray, and samples the noise at that exact UV — mesh/scale-agnostic, exact tilt from four cached neighbour rays, sRGB noise linearised to match the GPU. `textureCoord` needs the lava mesh Read/Write Enabled (it shipped OFF), so Implement Fix 046 turns it on for the lava FBXs and Rebind warns if a mesh isn't readable. Considered the world-space-noise alternative (sample noise by world XZ in both shader and CPU — more robust, no Read/Write needed) but the dev chose to keep the current look untouched. `displacementMultiplier` should go back to 1 now that the sample is correct (it was fudged to 2 to compensate for the wrong UV).

[2026-06-19] — PLAYER TUNNELED THROUGH MOVING ROCKS/PLATFORMS — MOTOR DEPENETRATION FIX
The player passed through the bobbing rock intermittently. Root cause was PlayerMotor, not the rock: both are kinematic Rigidbodies so PhysX never resolves their overlap — the player's own sweep casts are the only collision response, and they skip any hit at distance 0 (a sweep that starts already inside a collider). The rock drives itself into the capsule via MovePosition (applied during Physics.Simulate, AFTER the player's FixedUpdate) and the vertical sweep only reaches |vY|·dt, so the capsule could end a tick embedded; the next tick every sweep started inside the rock, returned distance 0, was skipped, and the player slid through — intermittent because it depended on the bob phase and approach speed (dash worsened it). Fixed by adding a depenetration pass (Physics.ComputePenetration over OverlapCapsule) at the start of PlayerMotor.Move that pushes the capsule out of any overlap before the sweeps run; it's a no-op while resting (capsule sits a skin-width off the ground) and fixes ALL moving kinematic platforms, not just the rock. Complements the earlier up-carry execution-order fix: that handles the grounded rider, this handles non-grounded contact and side/approach tunneling.

[2026-06-19] — BOB ONLY ON THE RIVER (V.4), NOT THE RIPPLE
The CPU-mirrored bob looked bad on the Lava Ripple surface, so we removed bobbing there. Now ONLY the Lava River (RAA_LavaFlow_V.4 turbulence) drives the rock bob. Rocks over the Ripple surface (and flat V.3 / unknown / unreadable-noise surfaces found over lava) are "Static" — they rest exactly where placed but remain solid, standable platforms. The simple self-driven sine bob is now reserved purely for the safety case where no lava is found beneath the rock at all. Deleted the dead Ripple displacement sampler (CacheRipple/RippleDisp + the per-object hash code) from RockBobber.

[2026-06-19] — BOBBING-ROCK UP-CARRY FIX (EXECUTION ORDER, NOT PARENTING)
The player couldn't stay on a bobbing rock during the UP-stroke. Root cause was tick timing: at the bob's trough the rock's velocity flips to rising, but if RockBobber ran AFTER PlayerController the rider read last tick's (still-falling) ride velocity, so the player wasn't lifted in time — the rising rock penetrated the feet, the ground SphereCast then started inside the rock and returned nothing, the player went "not grounded", and the carry collapsed. The carry math was already exact (player rises by rideVel.y*dt = the rock's exact rise); it just had to run first. Fixed with [DefaultExecutionOrder(-50)] on RockBobber so it moves and publishes ride velocity before the player each tick — up-carry is now penetration-free. Considered temporary transform-parenting (the dev's suggestion) but rejected it: the player is a kinematic Rigidbody driven by a world-space MovePosition motor, which ignores a parent transform, so parenting wouldn't carry it anyway. Down-stroke was already fine via ground-snap.

[2026-06-19] — BOBBING ROCKS ARE NOW RIDABLE PLATFORMS (+ BLENDER-ANIMATION FRIENDLY)
The bobbing rocks were visual-only — a static collider teleported by transform.position, which a kinematic player can't stand on (it isn't carried, and a fast bob drops away faster than ground-snap). Reworked RockBobber into a kinematic-Rigidbody MOVING PLATFORM: it auto-adds an interpolated, no-gravity, kinematic Rigidbody, moves via MovePosition/MoveRotation in FixedUpdate, and implements IRidePlatform so the existing PlatformRiderModule carries a grounded player up/down with the bob (same path as MovingPlatform). The lava collider is still never touched. Existing scene rocks need no manual wiring (RequireComponent + Awake configure the body). Blender animations: keep the bob on a PARENT and the animated model as a CHILD — the Animator drives the child freely while the parent bobs; only a clip that drives the same root world-Y/rotation would fight it (disable Apply Root Motion).

[2026-06-19] — ROCKS BOB ON THE LAVA'S VISUAL SURFACE (CPU MIRROR OF THE VERTEX SHADER)
Rocks need to float and bob on the lava. The lava's height is displaced in the VERTEX SHADER (GPU), so it never touches the CPU mesh or the lava collider — there's nothing to read back. Chose to mirror the shader's displacement math on the CPU: a RockBobber component finds the lava beneath it (one downward raycast against the Lava layer at Start), reads the lava material's params, auto-detects which lava shader it is, and each frame samples the SAME height the GPU computes at the rock's XZ to drive only transform.y. The lava collider is never modified (as requested). Auto-detect covers both displacing surfaces: Lava Ripple (RAA_LavaRipple, analytic sine — mirrored EXACTLY) and Lava River (RAA_LavaFlow_V4, noise-texture turbulence — APPROXIMATE: needs the noise texture Read/Write Enabled and assumes a plane-like UV map). Unknown/flat surfaces fall back to a simple self-driven sine bob. Caveat: Ripple's per-object phase comes from a world-origin hash (fp sin of a large number) that may differ slightly GPU-vs-CPU; if a rock floats a constant amount off the surface, set the material's Phase Desync (_RipplePhaseRandom) to 0 for exact seating. Editor: Tools > Blast Frame > Hazards > Create Bobbing Rock.

[2026-06-19] — WEAPON-VS-OWNER COLLISION LAYERS
Split projectiles onto side-specific layers so a side's shots never hit that side. Added four layers (Player, Enemy, PlayerWeapon, EnemyWeapon) and disabled two collision-matrix pairs: PlayerWeapon×Player and EnemyWeapon×Enemy. Because projectiles use trigger colliders and the layer matrix governs trigger events too, this needs zero projectile-code changes. Player capsule → Player layer, every EnemyCore → Enemy layer, the 5 weapon prefabs → their weapon layer. AoE blasts deal damage by OverlapSphere (a LayerMask), NOT collision, so the matrix can't stop self-splash — we also narrowed each blast's damageLayers: the player charged-shot Explosion excludes Player, the enemy ArcExplosion excludes Enemy. Layer assignment is surgical (root + collider GameObjects only) so the player's camera/viewmodel children keep the Viewmodel layer and the gun overlay (Fix 041/042) stays intact. Implement Fix 045.

[2026-06-18] — LAVA FLOW V.3 (V.1 + V.2 STACKED IN ONE SHADER)
Combined the two lava flow shaders into "RAA Lava Flow V.3": the V.2 layer (emission + tint + alpha) composited on top of the V.1 layer (emission base), blended by the top's alpha map. Both layers expose their full option set independently — separate textures/tiling, emission colors, and flow (Move) speeds — so a single material drives the whole stacked look. Output is opaque (V.1 is the base); the top's alpha just controls where V.2 shows vs. V.1 underneath. Inspector lists all V.2 (top) options first, then all V.1 (bottom) options.

[2026-06-18] — LAVA RIPPLE: CONTACT SOFT BLEND (REPLACED THE DITHER)
Switched the contact effect from a hard dither-clip to a soft alpha fade (soft-particle blend) so the lava eases into surfaces it meets instead of a harsh edge. Now alpha-blended (ZWrite Off) in the Transparent queue, still needs Depth Texture. Controlled by Contact Soft Blend Distance (0 = off). Open limitation: the depth texture only contains opaque depth, so the fade reacts to terrain as well as opaque lava — it can't isolate "lava only" by depth alone; doing that cleanly needs a renderer feature that renders a lava-layer depth texture. (Was briefly a dither.)

[2026-06-18] — HEAT SHIMMER VIA DISTORTION BILLBOARD PARTICLES
For "heat rising off the lava" we chose distortion billboard particles over a full-screen volume effect (localized, cheaper, easy to revert). New "RAA Heat Distortion" shader refracts the opaque scene texture by a scrolling noise, faded by particle alpha. Implement Fix 044 builds the material + a rising-shimmer ParticleSystem prefab (world space, box emitter, rise + waver + grow + fade). Drag onto lava, scale emitter, tune strength. Not a Volume (URP has no built-in heat-distortion override); this is the localized approach.

[2026-06-18] — REMOVED THE CONTACT SOFT-BLEND / LAVA-DEPTH SYSTEM ENTIRELY
The depth-based intersection soft-blend never looked right in practice and the extra render pass (LavaDepthRendererFeature) cost resources, so we pulled the whole thing. Deleted LavaDepthRendererFeature.cs; reverted Lava Ripple and Lava Flow V.4 back to plain OPAQUE (removed _ContactDistance, _LavaDepthTexture sampling, transparent queue + blending). Lava intersections stay hard edges for now — acceptable. NOTE: the LavaDepthRendererFeature must also be removed from PC_Renderer (and Mobile_Renderer if added) in the editor — deleting the script leaves a missing-script feature entry there.

[2026-06-18] — SOFT-BLEND THE V.4 POOL AGAINST THE V.3 FALL (KILL THE HARD SEAM)
Hard intersection edge where the turbulent V.4 pool meets the V.3 fall. Added the lava-only contact soft blend (the same one on Lava Ripple) to V.4: it's now alpha-blended/Transparent, fading against _LavaDepthTexture. Pool = V.4 (transparent, fades), fall = V.3 (opaque, lives in the lava depth on the Lava layer). V.4 leaving the opaque set is fine since the fall is the solid one. Needs Contact Soft Blend Distance > 0 and the LavaDepthRendererFeature + Lava layer set up.
FOLLOW-UP: first pass looked WORSE because ZWrite was Off (standard transparency) — the churning turbulent vertices then sorted wrong (overlapping waves X-rayed). Fixed by keeping ZWrite ON: the surface is solid except at the soft edge, so it needs depth writes for the turbulence to render correctly while still alpha-fading the seam. (Lava Ripple's own soft blend still uses ZWrite Off; switch it too if its ripple shows the same sorting artifact.)

[2026-06-18] — LAVA-ONLY SOFT BLEND VIA RENDERER FEATURE
Resolved the above limitation the robust way: added LavaDepthRendererFeature (URP RenderGraph) that renders the opaque lava (a Lava layer, opaque queue, DepthOnly) into a global _LavaDepthTexture. The Lava Ripple shader now soft-blends against THAT instead of the scene depth, so it fades only against other lava (fall/river) and ignores terrain. The opaque-queue filter also excludes the transparent ripple itself. Requires adding the feature to PC_Renderer/Mobile_Renderer and putting lava on the Lava layer. Built but not yet verified in-editor (RenderGraph API is version-sensitive).

[2026-06-18] — RENAMED "LAVA RIVER V.2" TO "LAVA RIPPLE"; ADDED LAVA FLOW V.4 (TURBULENCE)
Renamed the river-V.2 shader to "Lava Ripple" (it's the centered-ripple pool, distinct from the flow-map river). Added Lava Flow V.4: exactly V.3 plus vertex turbulence — a scrolling noise texture (own tiling/offset + Move scroll) pushes the mesh vertices up/down to churn the lava surface. Standard heightfield-displacement approach; the only correctness requirements are sampling the noise with SAMPLE_TEXTURE2D_LOD in the vertex stage and using a subdivided mesh. Unlit means no normals to recompute.

[2026-06-18] — LAVA RIVER V.2 (V.3 + CENTERED RIPPLE, NO FLOW MAP / NO IMPACT POINT)
Made a second river shader that is literally Lava Flow V.3 plus a ripple. Dropped the flow map (flow is the V.3 Move scroll again) and dropped the world-space impact point — the ripple is centered on the mesh itself (object-space, radiating from the local origin), so the workflow is just "drop a subdivided plane with this material where you want a rippling lava pool." Kept all V.3 property names so a V.3 material pastes in exactly.

[2026-06-18] — LAVA RIVER SHADER (FLOW MAP + CONTINUOUS RIPPLE)
Added a third lava shader, "RAA Lava River", for a flowing river (the two flow shaders combine into a lavafall; this is the pool/river it feeds). Two new ideas vs. the flow shaders, decided in a design chat: (1) flow follows the riverbed via a painted FLOW MAP instead of a uniform scroll — the developer will author flow maps; flat surface so slope-based auto-flow was ruled out. (2) the mesh continuously ripples with concentric waves around a fixed world-space impact point (where the lavafall hits), done as vertex displacement — requires a subdivided mesh, which the developer will model. Kept it opaque (river top surface). Impact point is a hand-set material property for now; a transform-driven component is the likely next step.

[2026-06-18] — LAVA-FLOW SHADER: RESTARTED AS A STANDALONE UNLIT SHADER
Scrapped the first attempt (which duplicated the triplanar projection shader) — lava should be its own thing, unrelated to the projection fork. New plan: a from-scratch URP Unlit shader "RAA Lava Flow" built up piece by piece. Step 1 (done): unlit emission only — an emission map × HDR emission color, output directly. Scroll/flow/distortion will be layered on in later steps once the emission looks right.

[2026-06-18] — DASH IS NOW RELEASE-CANCELLABLE (HOLD-TO-DASH)
Releasing the dash button now ends the dash immediately instead of always running the full dashDuration. dashDuration becomes a maximum cap rather than a fixed length — tap for a short dash, hold for the full burst. Cooldown still triggers on the initial press regardless of how early it's released (the dash is consumed). Momentum carry is unchanged: ending the dash just stops overriding horizontal velocity, so a released dash bleeds out via air drag exactly like a naturally-expired one, preserving dash-jump carry. Implemented by adding OnDashReleased to IPlayerInput (wired to Sprint.canceled) and zeroing the dash timer on release in DashModule.

[2026-06-17] — PLAY-MODE LIGHTING DOWNGRADE: STANDALONE QUALITY TIER WAS POINTED AT MOBILE
Scene/edit view looked great but lighting visibly degraded the moment Play started. Diagnosed via MCP: it was NOT runtime code (GameManager only sets VSync) and NOT a per-camera setting — the project has two URP tiers, "Mobile" (Mobile_RPAsset: renderScale 0.8, MSAA off, soft shadows unsupported, 1 shadow cascade, 1024 shadowmap, no additional-light shadows) and "PC" (PC_RPAsset: renderScale 1, MSAA 8x, soft shadows, 4 cascades, 2048 shadowmap). The active editor tier was PC (m_CurrentQuality=1) so Scene view was full quality, but m_PerPlatformDefaultQuality[Standalone] was 0 = Mobile, and Play simulates the Standalone target → it swapped to Mobile_RPAsset on entering Play. Mobile even listed Standalone in its excludedTargetPlatforms, confirming the default was a template-leftover misconfig. Fix 040 repoints the Standalone default at the PC tier (Mobile tier kept intact for future mobile builds).

[2026-06-17] — RAA URP LIT PROJECTION: OBJECT-SPACE PROJECTION OPTION
Added a `Project In Object Space` toggle (keyword `_RAA_OBJECT_SPACE`, default off = world space). World space keeps the texture fixed in the world (object swims through it when rotated/moved); object space projects in the mesh's local frame so the texture is locked to the object and follows its rotation/position/scale — fixing the "texture swims when I rotate the object" problem. Implemented by transforming world position/normal into object space before projecting (and converting the resulting normal-map normal back to world for lighting). Applied to both ForwardLit and DepthNormals so SSAO stays consistent.

[2026-06-17] — RAA URP LIT PROJECTION: OBJECT-SPACE IGNORES SCALE
Refined object-space projection to IGNORE object scale (it previously stretched the texture with the object because it used raw local coordinates). Now it builds a scale-free basis by normalizing the columns of ObjectToWorld (pure rotation axes) and projects `worldPos - objectOrigin` onto them — so distances stay in world units regardless of scale, while still following rotation and position. The normal-map normal is rotated back to world with the same orthonormal basis. Offset and Units Scale are world units in both world and object modes now. Assumes no shear (uniform/axis-aligned scaling).

[2026-06-17] — RAA URP LIT PROJECTION: TRIPLANAR NORMALS IN DEPTHNORMALS + WHITEOUT FIX
Two normal-mapping fixes. (1) Switched the triplanar normal blend from a cheap sign-flip approximation to the proper whiteout blend (folds the geometric world normal into each plane) so bump detail stays anchored to the surface and lines up with the albedo. (2) Ported triplanar into the DepthNormals pass: stock URP sampled the normal map by mesh UV there, so on UV'd geometry the _CameraNormalsTexture (which feeds SSAO/screen-space) carried a finer UV-scale bump than the world-projected forward pass — showing as a smaller "duplicate" shading on top of the correct normals. DepthNormals now derives its world normal by the same triplanar projection. ShadowCaster/DepthOnly alpha and the Meta bake pass are still stock UV (acceptable for opaque blockout).

[2026-06-17] — RAA URP LIT PROJECTION: PER-AXIS WORLD UNITS SCALE
Replaced the fixed 4-units-per-tile constant with a per-material `World Units Scale (units per tile XYZ)` vector (default 4,4,4). Each axis value is the number of world units the texture covers before repeating, so a smaller number renders denser on that axis (e.g. 4,4,1 makes Z repeat every 1 unit). Implemented as a component-wise divide of world position in `RAA_ProjectedPos`, clamped to ≥1e-4 to avoid divide-by-zero. Exposed in the material's RAA Triplanar Projection section alongside the projection toggle and offset.

[2026-06-17] — RAA URP LIT PROJECTION: SWITCHED TO A TRUE URP/LIT FORK
Reversed the earlier same-day decision (below). Instead of a self-contained Lit-equivalent shader, the projection shader is now a LITERAL FORK of URP 17.3.0's `Lit.shader`: the actual shader + a verbatim copy of `LitInput.hlsl` (`RAALitInput.hlsl`) and `LitForwardPass.hlsl` (`RAALitForwardPass.hlsl`) live in the project, with all other passes still including the stock URP pass files. This gives the complete URP Lit feature set (specular/metallic workflow, parallax, detail maps, clear-coat SRP stubs, full GI/lightmaps/APV, all passes incl. GBuffer/MotionVectors). Triplanar is injected only into the ForwardLit fragment (the renderers are Forward and Forward+, so GBuffer never runs here). [2026-06-17] — RAA URP LIT PROJECTION SHADER + PLAYER CAMERA REBUILD
New shader `RAA Materials/RAA URP Lit Projection` for blockout texturing: full URP Lit PBR shading (base/metallic-gloss/normal/occlusion/emission maps, main + additional light shadows, soft shadows, SSAO, reflection probes, fog, SH GI) across all the passes that matter (ForwardLit, ShadowCaster, DepthOnly, DepthNormals, Meta). Adds a "Projection" toggle (ON by default): when on, every map is sampled by world-space triplanar projection at a CONSTANT scale of one full texture tile per 4×4 world units (2048px ⇒ 512 texels/unit), so texel density is uniform everywhere without UV unwrapping; when off it falls back to mesh UVs. Adds a per-material `Projection Offset (world XYZ)` to slide the projection per object. [2026-06-12] — ARC TURRET: HEAVY MORTAR REDESIGN
The arc-predict turret is now a slow heavy mortar: half turn rate (45°/s), half fire rate (0.5 shots/s), and a projectile that is 3x bigger, travels at half speed (6 m/s), and falls under half gravity for a floaty, readable lob. It only fires with line of sight to any part of the player (5-point visibility check against the player's collider bounds — partial cover does not hide you). The projectile no longer deals contact damage; on impact it spawns a pooled ArcExplosion with a 1.5-unit blast radius (damage tuned on the ArcExplosion prefab, not on the turret's stats). Launch angle is always the high ballistic arc, minimum 45°.

[2026-06-12] — PLAYER MOVEMENT: MEASURED DISTANCES (in-game tested)
Standing long jump covers 7 Unity units horizontally. A dash covers 10 Unity units. These are real in-game measurements and should be used as the reference grid for level layout — gaps, platforms, and room widths should be designed relative to these values. A gap a skilled player can just barely jump is ~6–7 units; a gap requiring a dash-jump would be ~8–10 units.

[2026-05-31] — HQ / ECONOMY / SHOP: ARCHITECTURE DECISIONS
Meta-currency (metaCurrency) is the single economy unit: earned per run, spent only at HQ on permanent upgrades. CurrencyManager owns the live wallet and registers as ICurrencyManager; it bootstraps from SaveData if a SaveManager is present and falls back to 0 otherwise, so the shop works without a save system wired. Permanent upgrades are authoring-time SOs (PermanentUpgradeSO) with IntReference cost and FloatReference magnitude — constants by default, optionally driven by Variable SO assets if a designer wants global tuning. ShopManager owns purchase logic and defers ownership persistence to ISaveManager (TryGet — optional), keeping the shop functional even without persistence. ShopUI is fully event-driven: it never polls in Update; OnCurrencyChanged and onPurchasedEvent drive all row refreshes. The "cannot afford" state is a visual dim, not a hidden row, so players can see what they are working toward.

[2026-05-31] — LEVEL & RUN MANAGEMENT: ORCHESTRATION DESIGN
RunManager is the single source of truth for run state (active, difficulty, level/room index). It sits in Core and registers as IRunManager so any system can reach it via ServiceLocator without a direct reference. LevelController lives per-level-scene and drives room advancement by listening to a GameEventSO rather than calling RunManager directly — this keeps it fully decoupled from the room feature. Difficulty is chosen at StartRun() call time and exposed as a read-only property; room-count and difficulty-scaling multipliers live on the LevelDefinitionSO so designers can tune each of the 9 levels independently.

[2026-05-31] — POWERUPS: RUN-SCOPE AND STUB STRATEGY
All pickups (Heal, MoveSpeedBuff, MaxHealthUp) are run-scoped and lost on death — they must never be written to save data. Heal is fully implemented via PlayerHealth.Heal. MoveSpeedBuff and MaxHealthUp are intentionally stubbed with TODO comments: mutating a shared FloatVariable without a modifier/overlay layer would permanently corrupt the stat for every subsequent run. A stat-modifier system (additive/multiplicative layers that reset on death) will be the correct unlock point for those effects.

[2026-05-31] — HUD: WIDGET BINDING STRATEGY
HUD widgets bind defensively to player components via EntityRegistrySO — they retry each frame in Update until the registry reports HasPlayer, then subscribe and stop polling. This means the HUD can live in Core and start before the player without race conditions. Each widget also accepts a direct registry injection via SetRegistry() from HUDController.Awake as a faster path when both exist simultaneously. The ChargeBar starts hidden and only becomes visible when charge > 0, keeping the screen clean during normal movement.

[2026-05-31] — PLAYER SHOOTING: CHARGE SYSTEM DESIGN
The charge shot is designed as a continuous spectrum rather than a binary tap/charge. Any release fires a projectile; charge level 0..1 linearly scales damage (base 1 to 5), size (0.25x to 1x), and speed (30 m/s tap down to 22 m/s fully charged — slower = heavier feel). The AoE explosion triggers at any charge ≥ 0.5, making partial charges a meaningful choice. Full charge time defaults to 1 second. These numbers are all FloatReference/IntReference fields and designer-tunable without code changes.

[2026-05-31] — PLAYER SHOOTING: POOLING STRATEGY
PlayerProjectile and AoeExplosion are fully pooled (no runtime Instantiate during play). PlayerProjectile prewarms 20 instances (fast tap-fire feel without expansion), Explosion prewarms 8. Both expand by half their prewarm count when exhausted and log a warning. The player camera IS the muzzle — no separate muzzle transform needed since the FPS view means the camera forward IS the aim direction.
